# Harness-skills

`Harness-skills` 根据当前项目实际可用的 API、模型 benchmark、预算和任务负载，生成可审计的多模型执行路由。标准调用名为 `$harness-skills`。它适用于需要把任务拆分、委派给不同模型、独立复审并保留证据链的工作。

## 安装与使用

从 [`RaFenglei/Fenglei-skills`](https://github.com/RaFenglei/Fenglei-skills) 安装 `Harness-skills/harness-skills` 到 Codex 用户 skills 目录。安装后可这样调用：

> `$harness-skills` 读取本项目实际可用 API 和已安装 skills，依据最新 benchmark 重新设计 harness，明确每个模块的执行、递补、补充和独立复审，并按我选择的模式运行。

每轮开始先询问使用“仅 Codex”还是“Harness”。仅 Codex 模式不调用第三方模型；Harness 模式才按当前项目授权的路由执行。API 变化时先更新项目内 `.harness/providers.json`，重新核对来源、协议、模型、端点、配额组和客户端能力，再提出路由变更。

技能不会预置账号、密钥、内部地址或固定模型版本。技能仓库只保存通用规则；项目 API 清单、调用回执、样本结果和可选记忆保存在实际项目的 `.harness/`，不上传到本仓库。

## 四角色路由规范

每个任务必须明确记录 `platform`、`client`、`model`、`protocol`、`endpoint` 和 `quota_group`。网关页面显示的模型名称只说明请求标签，不能单独证明后端身份。

每个任务至少包含四个角色：

1. **主执行（primary）**：在指定平台上完成主要分析、代码、文稿或报告。
2. **主执行递补（primary_fallbacks）**：只在主执行不可用、认证失败、配额冷却或任务失败时接替主执行；所有切换都要记录原因和时间。递补不会替代独立补充。
3. **独立补充（supplement）**：独立会话、独立证据和独立输出，负责补充检索、反例、方法核查或候选实现；即使主执行成功也照常运行。
4. **独立复审（reviewer）**：新会话、不同模型家族，且不能使用实际作者或实质整合者；复审结果绑定输入和产物 hash，输出 `pass`、`revise` 或 `block`。

复审发现问题后，先由整合者修订，再由复审者复核；“已完成”只表示角色链和验收条件满足，不把同一模型家族的第二个会话冒充跨模型复审。

## 模型分工原则

路由由 benchmark 和任务难度决定，而不是按模型名称固定绑定。通常可按下列原则生成候选：

- Codex 原生工具：项目规划、真实文件和命令执行、代码合并、最终整合与发布检查。
- 高推理模型（如 GPT-6 Astra、GPT-5.6 Sol 或同等能力模型）：复杂设计、长上下文推理、难以分解的故障定位。
- Claude Opus/Fable/Sonnet：机制分析、论文论证、复杂代码审阅和高质量补充；按实际 benchmark 区分复杂度。
- Kimi、GLM、DeepSeek 等：大批量文献/元数据整理、重复统计、格式转换和可并行的小任务。
- 视觉任务：先验证可用的视觉端点、输入协议和输出质量，再把图像理解分给通过验证的模型；未验证的模型只列为候选，不自动用于关键结论。

模型可用性、价格和限额会变化。共享网关配额进入冷却时，优先使用已授权的同平台候选；独立 Kimi 或其它已授权端点可作为递补。不得使用 Codex 重置卡、自动购买额度或复制其它对话中的密钥。

## Skill 更新与隔离

Harness 运行前先检查当前项目实际安装的相关 skills，并报告版本、hash、兼容性和精确 diff。更新由用户决定：可以保持现状、只批准指定文件，或批准全部候选。运行 Harness 本身不是更新授权。

获得批准后，先创建带日期的备份，再只修改获批路径并重新运行格式校验、离线边界测试和角色路由检查。其它 skills 必须放在 `Fenglei-skills` 的同级独立目录，拥有自己的 README、资源和版本边界；不得把某个项目的 API、样本数据或默认路由写进其它 skill。

跨样本记忆默认采用“共享方法与已复审结论、样本结果隔离”。可选记忆可以关闭、限定到指定组或删除；原始表达矩阵、患者信息、密钥和内部地址永不进入共享记忆。

## 验收边界

至少完成以下检查后才能放行：

- skill 结构和 front matter 通过官方格式校验；
- 路由 schema 可解析，每个任务都有主执行、递补、独立补充和独立复审；
- 递补只在主执行失败时触发，补充不被跳过；
- 复审者与实际作者分离，审查记录绑定输入/输出 hash；
- 配额、认证和端点错误都有可追踪回执；
- 备份和变更范围可核对。

离线校验只能证明结构和规则，不能证明所有 API、网关工具、视觉输入或实际科学分析已经成功。真实任务仍需在授权环境中运行并保存回执。
